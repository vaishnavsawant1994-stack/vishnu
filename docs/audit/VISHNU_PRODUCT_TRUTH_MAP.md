# Vishnu Product Truth Map

Audit baseline: `main` at `a8d3310b4d9090a42800621b1b27cb6045443c1e` (2026-10-16).

This document is an evidence map, not a marketing-completeness statement. Source code on the audited SHA is authoritative. Historical PR descriptions explain intent but do not override current code. Static existence is not execution evidence. Simulator/mock evidence is not physical-device or live-provider evidence.

## Status model

- `COMPLETE`: required implementation layers are present for the declared scope and executable/CI evidence exists.
- `PARTIAL`: meaningful implementation exists but a required layer or parity/evidence item is incomplete.
- `INTERNAL`: intentionally infrastructure-only; direct UI is not required.
- `EXPERIMENTAL`: deliberately gated/lab behavior.
- `BLOCKED`: engineering is substantially present but an external/owner dependency prevents qualification.
- `MISSING/BROKEN`: expected path is absent, unreachable, false-success, or failing.
- `LEGACY`: superseded/historical code or documentation.
- `NOT VERIFIED`: evidence was not available in this audit environment.

## Executive truth

Vishnu is no longer the small V2 topology described by root `ARCHITECTURE.md`. The current product is a multi-surface personal-AI runtime with governed tools/actions, durable approvals, Work/Projects, Memory and Knowledge, Universal Content Intelligence, OpenAPI/MCP capabilities, Capability Forge, device trust/transport, a local-first Data Plane, Sensorium, voice/provider boundaries, product building, recovery/continuity, and extensive qualification workflows.

The strongest recurring architectural boundary is: user/runtime intent -> canonical authority -> policy/approval -> governed execution -> durable/auditable state. Important examples are `tools/registry.py`, `security/approvals.py`, `devices/registry.py`, `devices/gateway.py`, `integrations/discovery/*`, `data_plane/*`, shared SQLite stores, and server owner/device APIs.

The product is **not** honestly describable as universally production-ready. Production deployment, production signing/store acceptance, broad real-provider OAuth verification, physical-device L4 qualification, and physical acoustic/telephony evidence remain external or unverified boundaries.

## Backend -> UI truth

1. **Governed actions**: Agent/runtime requests resolve through the shared ToolRegistry. The registry applies policy/risk/destination/classification controls and durable approvals. Direct infrastructure UI is not needed; owner-facing approval/action surfaces are appropriate.
2. **Universal Capabilities**: `integrations/discovery/*` owns OpenAPI/MCP normalization/catalog/execution. `server/apps_tools_api.py` provides owner/device-scoped transport. Desktop `ui/capability_manager.py` and native companion work from PR #183 provide management surfaces. Missing live provider consent is an external blocker, not evidence that the core registry is absent.
3. **Devices**: `DeviceRegistry` is identity/trust/state; `DeviceGateway` is communication/dispatch. Pairing and settings are product surfaces. These are deliberately separate from owner identity.
4. **Data Plane**: policy + local stores + leases/encryption/provider adapters are backend authorities. UI is expected to expose policy/location/status, not internal crypto/merge machinery.
5. **Memory vs Knowledge**: separate stores/runtime boundaries are enforced. They may interoperate in context construction but are not one authority.
6. **Sensorium**: sensing/provider/evidence infrastructure is primarily agent/internal. Owner inspection/permissions belong in Settings/Advanced/contextual UI. Sensorium is not an action bypass.

## UI and navigation truth

### Desktop

Current source establishes the primary navigation as:

`Home -> Conversation -> Memory -> Knowledge -> Activities -> Dashboard -> Apps & Tools -> Settings`

Supporting UI modules include first-run, capability manager, control panel, memory panel, mobile pairing, native auth and Products. A source file alone is not counted as reachable; the primary eight pages are instantiated/wired by `ui/main_window.py`. Full dialog-by-dialog reachability remains `NOT VERIFIED` in this first audit PR unless explicitly traced in the machine-readable inventory.

### PWA/Web

The PWA is not a single static page. It contains chat/context ownership, agent-workforce/work mode, adaptive composer and additional progressive-disclosure assets. The correct product principle is not to expose every infrastructure subsystem as top-level navigation. Advanced/owner/qualification systems may remain under More/Settings/Advanced/contextual agent flows.

### Android/iOS

Native companions are real codebases and participate in owner session/device enrollment/capability/Sensorium/data-plane work. Emulator/simulator evidence counts only for those environments. Physical phones/tablets remain separate qualification targets.

## API truth

The repository contains a broad modular FastAPI surface under `server/`, including primary `api.py` plus activities, agents/workforce, approvals, capabilities/apps-tools, device/onboarding/data/storage, Sensorium, voice and product/runtime APIs. `server/apps_tools_api.py` was source-verified in this audit and demonstrates the expected security pattern: trusted request, active trusted device, scoped authorization, recent owner reauthentication for sensitive connection/import operations, bounded request sizes, SecretVault credential references, audit events, and ToolRegistry rehydration.

A framework-aware route enumerator is still required before claiming that **every** route has been exhaustively classified by method/path/consumer. Until that generator is committed and run, the exhaustive route count is `NOT VERIFIED` rather than guessed.

## Data/storage truth

Canonical persistent domains include shared SQLite-backed Memory, Knowledge, Products/Projects/device state; durable approval/execution controls; capability catalog and connector state; SecretVault/root key material; local-first Data Plane state; content/semantic indexes; evidence/audit stores; native/browser secure state and optional provider-backed storage.

Merged hardening from #203-#219 establishes versioned shared SQLite adoption, sensitive Memory encryption, backup/DR, endurance, and fault-injection coverage. PR #245 extends provider transfer/placement without changing the local-first rule. Duplicate-source-of-truth risk is guarded by architecture invariants, but an exhaustive table/index-level orphan analysis remains `NOT VERIFIED` in this documentation-only audit head.
